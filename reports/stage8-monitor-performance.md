# Этап 8 — экономичный монитор и адаптивные миниатюры

## Изменения

Добавлен core/monitor_profile.py: экономичный режим по умолчанию, обычный и выключенный. Выбор сохраняется в настройках, не затирая выбранные папки.

| Режим | Активных записей с видеопотоком | Предел FPS | Ширина | Декодирование |
|---|---:|---:|---:|---|
| Экономичный | 1–4 | 1 | 220 | Только опорные кадры |
| Экономичный | 5+ | 0.5 | 220 | Только опорные кадры |
| Обычный | 1–3 | 4 | 320 | Все требуемые декодером кадры |
| Обычный | 4–8 | 2 | 280 | Все требуемые декодером кадры |
| Обычный | 9+ | 1 | 220 | Все требуемые декодером кадры |
| Выключен | Любое число | 0 | — | Процессы отсутствуют |

Экономичный режим использует input decoder option skip_frame=nokey. Select-фильтр ограничивает частоту без генерации дубликатов через fps; fps_mode=vfr позволяет отправить первый опорный кадр без ожидания следующего для ресемплинга. Реальный FPS может быть ниже предела при длинном GOP. Таймаут отсутствия кадров в таком режиме увеличен до 90 секунд, чтобы не путать длинный GOP с сетевой ошибкой. Для обычного просмотра сохранён прежний таймаут.

Считаются только реально записываемые видеопотоки: пауза и screen capture не создают декодеры. Изменение числа задач пересчитывает общий профиль; тот же профиль не перезапускает уже работающие процессы. Поколение callback блокирует поздние кадры от остановленного/заменённого потока.

Монитор подписывается на миниатюры только пока открыт и отображён. Map/Unmap изменяют владение один раз, исключая утечки счётчика. При скрытии освобождаются кадры и прекращается отдельное прослушивание. При закрытии отменяется UI-таймер. Скрытое окно не перерисовывает кадры; обычный poll адаптирован к частоте профиля. Из сетки исключены завершённые задачи; они сохраняются в основной панели и истории.

Частота подробного встроенного PreviewPanel (15 FPS) не менялась. Архивные on_timed_frame и seek не переводятся на опорные кадры; несовместимая комбинация явно запрещена. LiveThumbnailStream получил ожидание завершения worker для проверок очистки ресурсов.

## Парный замер до/после

До: исходники коммита 4c8a441 в отдельной временной копии. После: новые экономичные миниатюры. Одинаковый Python 3.12.4, FFmpeg 7.1.1 и синтетический H.264/AAC 1280×720, 25 FPS, 3 Мбит/с, GOP 50 (2 секунды). На сценарий записывается 8 секунд медиаконтента. Используются настоящий Recorder, декодеры и ffprobe, без нативного GUI и реальной сети. Разные сценарии запускаются отдельными Python-процессами.

| Записей | Монитор | CPU до, с | CPU после, с | Средний CPU до/после, % одного ядра | Пиковая RSS крупнейшего дочернего процесса до/после, МиБ |
|---:|---|---:|---:|---|---|
| 1 | Закрыт | 0.726 | 0.650 | 4.6 / 4.2 | 27.3 / 27.6 |
| 1 | Открыт | 1.619 | 0.970 | 10.3 / 6.2 | 95.7 / 55.8 |
| 4 | Закрыт | 2.759 | 2.727 | 17.5 / 17.4 | 27.9 / 27.8 |
| 4 | Открыт | 5.641 | 3.610 | 35.8 / 22.9 | 96.5 / 60.0 |

Для четырёх записей с монитором суммарное CPU-время уменьшилось примерно на 36%. Разность между открытым и закрытым монитором уменьшилась с 2.882 до 0.883 CPU-секунды (примерно 69%); эта разность — ориентир дополнительной нагрузки миниатюр, а не отдельный замер процесса. Размеры итоговых файлов совпали: 3 541 911 байт на запись; все результаты completed. На миниатюру вместо 29 кадров получено 3 — это ожидаемый компромисс плавности экономичного режима.

Методика: resource.getrusage для Python и завершённых дочерних процессов. RSS — пиковая память крупнейшего дочернего процесса, НЕ суммарная память приложения. По одному короткому прогону на сценарий, без доверительных интервалов. Старые цифры этапа 1 не используются для прямого процента: в новом парном тесте другой GOP и накопленные изменения финализации. Сырые данные: stage8-before.json, stage8-after-economy.json. Для повторения нового сценария: `.venv/bin/python tools/benchmark_monitor.py --seconds 8 --mode economy --output /tmp/monitor.json`.

## Общий конвейер записи и миниатюр

Оценён по текущей архитектуре, но не внедрён. Запись использует copy и progress в stdout; миниатюры требуют декодирования и другого выходного канала. Их объединение в один FFmpeg потребовало бы новых pipe, отключения/подключения вывода без рестарта записи и защиты от блокировки/ошибки JPEG-выхода. Приоритет — независимость сохранения видео от окна мониторинга. Измерений такого общего конвейера нет, поэтому выигрыш не заявляется. Основной PreviewPanel также пока не делит декодер с монитором.

Экономичный режим не обещает такого же сокращения сетевого трафика: видимый монитор по-прежнему читает источник отдельно. Режим off и скрытие убирают дополнительный процесс/чтение; фактическая сеть в этом тесте не измерялась.

## Проверки и ограничения

**Полный прогон: 196 тестов, 75.193 секунды, OK.** Журнал: stage8-tests.txt. Проверка git diff --check пройдена.

Новые тесты: адаптивные пороги; выключение без вмешательства в процесс записи; отбрасывание устаревших кадров; отсутствие дубликатов при нескольких подписчиках; исключение paused/screen capture; сохранение режима и остальных настроек; баланс Map/Unmap; удаление завершённых плиток; запрет keyframe-режима для точной архивной шкалы. Реальный FFmpeg проверен на первом JPEG, input skip_frame и завершении/очистке процесса.

Нативное сворачивание окна вручную не проверено: события видимости тестируются через модель обработчиков. Перекрытие окна другим окном не считается Unmap. Поведение Cmd+H и других специфичных для macOS способов скрытия требует ручной проверки. Реальные HLS-потоки, очень длинные GOP и плавность пользовательского интерфейса не измерялись в этом синтетическом прогоне.

Изменения находятся в ветке codex/stage-8-monitor-performance. Установленное приложение, исходная папка пользователя и пользовательские записи не менялись. Сборка DMG, push и релиз не выполнялись.
